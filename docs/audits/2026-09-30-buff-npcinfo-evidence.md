## Complete-capture rejection: all-buff flags are a separate source semantic

The later bounded artifact `.local/tmp/b1-a63-20260930-20/` was produced from
the same revision-bound `Module:Npcinfo/data` page (`pageId=18065`, revision
`1022313`). It reports 762 numeric rows and 1,417 positive assertions, but its
manifest's `fieldSemantics=buffImmune-exhaustive` is only a producer claim. The
raw module contains `buffImmuneAll` and `buffImmuneAllNotWhips` rows, so the
specific `buffImmune` list cannot by itself prove an exhaustive immunity set.
The capture hashes are retained here for diagnosis:

- raw page: `sha256:dba3f8b2f2e94b43b9ed244d7e2f060baac3d99507173c5c6c1fb0c4eedadcbf`
- manifest: `sha256:9dfbd93756c23d1ad44da5ad63d13c76f6ecc76b312c773c089b6218a63c581f`
- source assertions: `sha256:8cdffc0d1faade81e37ced69207245a4d8016b17df7c4e24b89a48518dc1c7c5`

The current verifier now rejects a complete claim as soon as a numeric row
has either flag, with `Npcinfo all-buff immunity flag requires expansion
evidence`. The retained `verified-complete.json` is historical producer
output; it is not re-certified after this stricter verifier change. This is a
fail-closed correction, not a source failure.

The upstream Wiki source explains why expansion is required. The revision-bound
`Module:Npcinfo/doc` documentation defines `buffImmune` as a comma-separated
specific list, `buffImmuneAll` as immunity to all buffs/debuffs, and
`buffImmuneAllNotWhips` as immunity to all except whip debuffs. The corresponding
`Module:Npcinfo/datagen` code maps `ImmuneToAllBuffsThatAreNotWhips` plus
`ImmuneToWhips` to those two output fields. Therefore a future complete source
contract must capture and hash those semantic sources, expand the all-buff
flags against the exact Buff scope, and separately bind the whip-debuff
classification. Until that contract exists, an absent Buff ID remains
`unknown`, including when it is absent from `buffImmune` in a row carrying an
all-buff flag.

The verifier also now detects duplicate numeric NPC definitions when they occur
on one line; the shared Lua object parser would otherwise keep only the last
object key. No canonical candidate or database write was created from `.20`.
